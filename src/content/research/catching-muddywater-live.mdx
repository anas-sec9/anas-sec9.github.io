In [the last post](/research/bugsleep-unmasked) I reverse-engineered **BugSleep**, MuddyWater's
backdoor — cracked its cipher, mapped its behaviour, and wrote detections from what I found. Writing
a rule is easy. Proving it fires on the real malware is the part most people skip. So this post is
the other half: I took the live sample into my detection lab, detonated it, and watched to see
whether my rules actually lit up across SIEM, IDS, and EDR.

Two things I care about in this one: doing it *safely* (it's live nation-state malware talking to a
real C2), and being *honest* about what worked and what didn't.

<Shot src="/shots/live-01.png" caption="The whole run in one picture — detonate, detect, prevent — across the four hosts of the lab." wide />

## The lab

A small Hyper-V environment on a domain, `lab.local`:

- **DC** — domain controller / DNS
- **Victim** — Windows 10, the detonation box
- **Sensor** — Ubuntu running Suricata, fed by a port mirror of the lab network
- **Splunk** — the SIEM, with Sysmon on the victim forwarding via a Universal Forwarder
- **Trend Vision One** — a real commercial EDR, deployed on the victim

<Shot src="/shots/live-02.png" caption="Hyper-V Manager — DC01, SENSOR and VICTIM up for the run. Kali stays powered off; this one needs no delivery stage." wide />

## Safety first — running live APT malware without setting my hair on fire

BugSleep beacons to a hardcoded C2 (`91.235.234.202`). The whole game is: that beacon must **never**
reach the real internet, but my sensor still needs to **see** it so the network rule fires. Here's
how I squared that:

1. **Sinkhole route** on the victim — `91.235.234.202/32` pointed at the sensor's IP. That forces
   the beacon onto the mirrored lab network (where Suricata watches) and away from the real internet.
2. **Sensor IP forwarding off** — so the sensor drops the C2 packet instead of relaying it out.
3. **Internet NIC disabled** during the run — full isolation. (The EDR queues its data and uploads
   it when I reconnect later.)
4. I **verified containment before touching the malware**: from the victim, `8.8.8.8` was
   unreachable, the DC and Splunk were reachable, and a test connection to the C2 tripped Suricata
   while never leaving the lab.

Only once that was green did I bring the sample anywhere near the box. I also disabled Defender's
real-time protection (lab-only, reverted after) so the sample would actually execute — otherwise it
gets quarantined on write and there's nothing to detect.

## Arming both sides

**Splunk** — I turned my analysis into real-time alerts: the msedge remote-thread injection (Sysmon
Event ID 8), the `PackageManager` persistence, the C2 IP, and the `a.txt` staging file.

<Shot src="/shots/live-03.png" caption="Four BugSleep alerts armed and enabled in Splunk before anything was detonated — C2 connection, PackageManager persistence, remote-thread injection into msedge, and the staging file in Public." wide />

**Suricata** — dropped my two BugSleep rules on the sensor and reloaded. Config test came back
clean, 51,000+ rules loaded, zero failed.

## Detonation

I opened Edge (so there's a live `msedge.exe` to inject into), double-clicked the sample, and kept
my hands off for two minutes.

Here's what fired.

**The injection — Splunk lit up 18 times.** Every hit was my *"remote thread into msedge"* rule
(EID 8). It fired repeatedly because BugSleep injects into several Edge child processes — an
unambiguous signal.

<Shot src="/shots/live-04.png" caption="Splunk Triggered Alerts — the remote-thread rule firing again and again as BugSleep works through Edge's child processes." wide />

**The C2 beacon — Suricata caught it.** Straight from the sensor:

```
[1:9100001:1] CTI BugSleep MuddyWater C2 - traffic to 91.235.234.202 ...
192.168.100.10:51859 -> 91.235.234.202:443
```

<Shot src="/shots/live-05.png" caption="Suricata fast.log — SID 9100001 firing on traffic to 91.235.234.202:443, interleaved with the stream events from the sinkholed session." wide />

And the best single frame of the whole run showed **the injected Edge going straight to the
hardcoded IP with no DNS**, right next to a *different* Edge process doing a normal DNS lookup for a
Microsoft domain. Same process name, two completely different behaviours.

> That contrast *is* the detection.

## The gaps I found (and this is the good part)

Two of my rules stayed quiet: persistence and `a.txt`. My first instinct was "they didn't run."
Wrong — both files were on disk:

```powershell
Test-Path "C:\ProgramData\PackageManager\PackageManager.exe"   # True
Test-Path "C:\Users\Public\a.txt"                              # True
```

<Callout type="correction" title="Not a detection failure — a telemetry gap">
The behaviour happened; Splunk never saw it. Two causes, both mine:

1. My Sysmon config (SwiftOnSecurity) wasn't logging file creation in `ProgramData` or `Public`. I
   added those paths, reloaded, and re-validated the `a.txt` alert.
2. `PackageManager.exe` was **dropped, not executed** this run — it runs later via persistence. My
   rule keyed on execution (EID 1), which never happened. The durable signal is the **drop (EID
   11)**, and when I looked, that event was right there all along.
</Callout>

<Shot src="/shots/live-06.png" caption="Sysmon Event ID 11 in Splunk — three creation events for the PackageManager binary on VICTIM. The drop the original, execution-based rule never looked for." wide />

Fixed both, and now all four behaviours are covered. Finding and closing that gap is the job — a
green dashboard that isn't logging the right thing is worse than no dashboard.

## The EDR — the honest part

This is where I want to be precise, because it'd be easy to overclaim.

I ran Trend in **Sensor Only** mode — telemetry and behavioural detection, but **no signature/AV
engine** — on purpose, so the sample would execute. In that mode, the sensor **collected** the
injection and even tagged it `MITRE.T1055` in its raw telemetry, but it **didn't raise an alert** on
it.

<Shot src="/shots/live-07.png" caption="Trend Vision One XDR Data Explorer — four telemetry events matching the sample's SHA-256. Collected, tagged, and never escalated." wide />

<Callout type="caveat" title="What this does and doesn't show">
This is **not** "the EDR can't catch BugSleep." Trend's product clearly can — I prove it below. What
this shows is narrower and more useful: **behavioural-only detection of a stealthy injection into a
signed browser isn't guaranteed.** My custom Sysmon + Splunk rule caught what the behavioural layer
didn't escalate. That's the whole argument for layered detection and in-house detection engineering
— you don't assume the default catches everything.
</Callout>

## Prevention — feeding the EDR my own intel

Then the fun bit. I took the SHA-256 from *my own* analysis, added it to Trend's Suspicious Object
list as **Block**, and re-ran the sample.

<Shot src="/shots/live-08.png" caption="The hash from my own reversing, added to Trend's Suspicious Object list — action Block / Quarantine, risk level High, source user-defined." wide />

Windows threw "cannot access the specified file," Trend popped **"Threat detected,"** and the log
said `act: block, success`.

<Shot src="/shots/live-09.png" caption="The victim — Windows refusing to open the file, with Trend's Endpoint Security raising a threat notification behind it." wide />

The malware got stopped by an indicator I produced by reverse-engineering it. That's the loop
closing on itself.

## And Trend's own verdict

Last, I submitted the sample to Trend's sandbox to see what *their* intelligence says with no help
from me. Verdict: **`Backdoor.Win64.MUDDYROT`, High** — and the actor field read **Earth Vetala**,
which is Trend's name for MuddyWater. So their engine independently confirmed both the malware and
the actor I'd attributed it to.

<Shot src="/shots/live-10.png" caption="Trend's sandbox verdict on the sample, reached with no input from me: Backdoor.Win64.MUDDYROT.THGAFBD, risk level High." wide />

The sandbox trace also mirrored my manual reversing beat for beat — `CreateMutexW(PackageManager)`,
the self-copy to `ProgramData\PackageManager`, `WriteProcessMemory` + `CreateRemoteThread` into
msedge.

<Shot src="/shots/live-11.png" caption="The sandbox process graph — the sample spawning its randomly-named dropped copy, which then injects into msedge.exe. The same chain I traced by hand in Ghidra." wide />

<Callout type="finding">
The one that got me: its `WriteProcessMemory` moved **145,732 bytes (0x23944)** into Edge — the exact
size of the code region my Ghidra analysis showed being decrypted. Two completely different methods,
same hex number.
</Callout>

## What I actually walked away with

- BugSleep was caught on **four independent surfaces** — my custom SIEM rule, the host artifacts,
  the network IDS, and the sandbox.
- I found a **real telemetry gap** in my own logging and fixed it.
- I documented, honestly, that the EDR's **behavioural layer** didn't auto-alert on the injection in
  the config I ran — and closed that gap three ways.
- I **prevented** the malware using an IOC I generated myself.

None of that came from a vendor report. It came from taking the thing apart, writing detections from
first principles, and then proving them on the real sample.

This run is also why the BugSleep rules in the [detection library](/detections) carry a
**lab-validated** label rather than a weaker one. The difference between that and
[sample-validated](/log/what-untested-means) is exactly this post — a rule that matched a file
versus a rule I watched fire on a live host — and I'd rather the labels tell you that than quietly
imply the same confidence everywhere.
